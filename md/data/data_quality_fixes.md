## 문제 1 — `bid_type` (입찰방식) 컬럼 없음 ★ 최우선

### 현상
`bids_history`에 입찰방식 구분 없이 적격심사·최저가·협상 데이터가 섞여 저장된다.

### 왜 치명적인가
사정률 분포가 방식마다 완전히 다르다.

| 입찰방식 | 사정률 패턴 | 예시 범위 |
|---------|-----------|----------|
| 적격심사 | 낙찰하한율 직상단에 집중 | 0.877 ~ 0.910 |
| 최저가낙찰 | 더 낮은 가격 경쟁 | 0.860 ~ 0.895 |
| 협상에 의한 계약 | 완전히 다른 로직 | 분포 무작위 |

세 방식이 섞이면 **bimodal 분포**가 되어 trimmed median이 어느 분포도 대표하지 못한다.
실내건축/조경은 대부분 적격심사이지만, 다른 방식이 소수라도 섞이면 통계가 오염된다.

### 해결책
- `bids_history`에 `bid_type VARCHAR(20)` 컬럼 추가
- 허용값: `"적격심사"` / `"최저가"` / `"협상"` / `"기타"`
- CRUD 쿼리에서 `bid_type = '적격심사'` 필터 기본 적용
- ETL(CSV 가져오기) 및 G2B 수집 시 반드시 파싱

## 문제 2 — `client_id` (발주청 코드) 없음

### 현상
발주처를 `client_name` 문자열로만 식별하는데, 동일 발주처가 여러 이름으로 저장된다.

```
"서울시"  ≠  "서울특별시"  ≠  "서울특별시장"
"경기도교육청"  ≠  "경기교육청"  ≠  "경기도교육청 수원교육지원청"
```

### 왜 치명적인가
Fallback Level 1(발주처 단위 통계)이 문자열 정확 매칭에 의존한다.
이름 불일치로 동일 발주처 데이터가 분산되면 각 그룹이 20건 미달이 되어
Level 1이 항상 실패하고 Level 2~4로 내려간다.
발주처별 맞춤 예측이 핵심 기능인데 사실상 죽어있는 상태.

### 해결책
- `bids_history`에 `client_id VARCHAR(20)` 컬럼 추가 (nullable)
- 나라장터 발주청 코드 (`dmndInsttCd` 등) 저장
- Fallback Level 1을 `client_id` 우선, `client_name` 보조로 변경
- 기존 데이터는 NULL 허용 후 점진적으로 채움

## 문제 3 — `price_method` (예정가격 결정방식) 없음

### 현상
복수예비가격 방식과 고정예정가격 방식이 구분 없이 저장된다.

### 왜 중요한가
예정가격 결정방식에 따라 사정률의 의미가 다르다.

| 방식 | 사정률 범위 | 특징 |
|------|-----------|------|
| 복수예비가격 | 0.980 ~ 1.020 | 추첨으로 평균, 매번 다름 |
| 고정예정가격 | ≈ 1.000 고정 | 설계금액 그대로 |
| 기초금액의 일정비율 | 좁은 범위 | 방식별 상이 |

혼재 시 분포가 두 그룹으로 나뉘어 예측 정확도 저하.

### 해결책
- `bids_history`에 `price_method VARCHAR(30)` 컬럼 추가
- 허용값: `"복수예비가격"` / `"고정예정가격"` / `"기타"`
- 통계 쿼리 시 방식별 분리 가능하도록 구조화

## 문제 4 — `project_type` 값 불일치

### 현상
G2B Fetcher와 ETL CSV가 서로 다른 공종명을 저장한다.

```python
# g2b_fetcher.py 반환값
"건축공사업", "조경식재공사업"

# etl_csv.py 저장값
"실내건축", "조경"
```

같은 공종이 두 가지 이름으로 저장되어 Fallback 쿼리에서 서로 다른 공종으로 취급된다.

### 해결책
- `"건축공사업"` → `"실내건축"` 으로 정규화
- `"조경식재공사업"` → `"조경"` 으로 정규화
- 정규화 함수를 `app/db/normalize.py` 에 중앙화

## 문제 5 — `region` 값 불일치

### 현상
지역명이 파일·API마다 다른 형식으로 들어온다.

```
"경기도 수원시" / "경기" / "경기도" / "경기[41000]"
```

Fallback Level 2(지역 단위)가 문자열 매칭이라 분산된다.

### 해결책
- 정규화 함수로 시/도 단위로 통일
- `"서울특별시"` → `"서울"`, `"경기도 수원시"` → `"경기"` 등

## 문제 6 — `participants` 추정값 100으로 저장

### 현상
`G2BFetcher.fetch()` 는 공고 시점에 참여업체 수를 알 수 없어 `DEFAULT_PARTICIPANTS = 100`을 저장한다.
이 추정값이 그대로 DB에 들어가면 투찰가 전략 계산 시 participants 기반 로직이 무의미해진다.

### 해결책
- 개찰 후 수집 시 실제 participants 값으로 덮어쓰기 (scsbid API에 `참여업체수` 포함)
- 추정값으로 저장된 행 식별을 위해 `participants_estimated BOOLEAN` 컬럼 추가 고려
- 단기: 추정값 그대로 사용하되, 개찰 후 수집 파이프라인에서 UPDATE 로직 추가
