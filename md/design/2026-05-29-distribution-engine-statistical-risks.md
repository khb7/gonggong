# Distribution Engine 통계적 위험 분석

**작성일**: 2026-05-29  
**대상 설계**: `docs/superpowers/specs/2026-05-29-distribution-engine-design.md`  
**목적**: 구현 전 통계적 위험 요소 식별 및 설계 수준의 대응 방향 제시

---

## 0. 결론 먼저

> **현재 설계는 Descriptive Analytics다. Strategic Optimization이 아니다.**  
> `estimated_win_prob`이라는 이름은 이 경계를 흐린다. 이름을 바꾸거나 해석 범위를 명확히 제한해야 한다.

---

## 1. Descriptive Analytics vs Strategic Optimization 구분

### 현재 시스템이 실제로 하는 일

```
과거 데이터 → "이 offset 구간에서 몇 명이 입찰했고, 몇 번 낙찰됐는가" 집계
```

이것은 **Descriptive Analytics**다. 과거에 일어난 일을 요약한다.

### Strategic Optimization이 되려면 필요한 것

| 필요 조건 | 현재 가능 여부 | 이유 |
|-----------|----------------|------|
| 예정가격 위치 예측 | **불가** | 복수예비가격 15개 중 2개 무작위 추첨 → 구조적 불확실성 |
| 이번 공고 경쟁자 분포 예측 | **불가** | 실시간 입찰 전에 타인 전략을 알 수 없음 |
| 내 입찰의 기대 낙찰 확률 계산 | **불가** | 위 두 가지가 불가하므로 |

### 진짜 의미

```
"estimated_win_prob: 3.2%"가 의미하는 것:
  → 과거에 이 구간에서 입찰한 사람 중 3.2%가 낙찰됐다.

"estimated_win_prob: 3.2%"가 의미하지 않는 것:
  → 내가 이 구간에 입찰하면 낙찰 확률이 3.2%다.
```

이 차이가 사용자 의사결정에 미치는 영향이 크다.  
**대응**: UI/API 응답에서 필드명과 설명을 `historical_win_rate`로 변경하고, "과거 낙찰 빈도"임을 명시해야 한다.

## 2. 위험 요소 항목별 분석

### 2-1. Bucket Binning Bias

**문제**

현재 설계: 0.1% 고정 간격 히스토그램.

```
offset 범위 -3.0% ~ +3.0% → 60개 bin
총 참여자 44,044명 → 평균 bin당 734건
```

표면적으로는 충분해 보이지만, 실제 분포는 극도로 skewed하다:

```
-2.0% ~ +1.5% 구간 집중 → 35개 bin에 ~90% 이상 밀집
-2.0% 이하, +1.5% 이상  → 25개 bin에 ~10% 분산
```

낙찰자 집중 구간(-0.5% ~ -0.8%)은 3개 bin뿐이고,  
여기에 71명의 낙찰자가 몰린다 → bin당 ~20-24건.  
이 구간 바깥은 bin당 1-3건으로 급감한다.

**추가 문제: 근사 오차**

```
정확: offset = bid_rate - lower_limit_rate
            = (투찰금액/예정가격) - (낙찰하한가/예정가격)

근사: offset ≈ (투찰금액/기초금액) - 낙찰하한율  [사정률≈1.0 가정]
```

사정률이 1.0이 아닌 경우(예: 0.9920 ~ 1.0080) 실제 offset과 근사값의 차이는 최대 ±0.008.  
이는 0.1% bin 폭의 ±8배 오차다. bin 경계 근처의 데이터가 잘못 분류된다.

**대응 방향**
- 근사값 대신 `bid_participants.bid_rate`와 `bids_history.lower_limit_rate`를 직접 JOIN해서 정확한 offset 계산
- 낙찰자 집중 구간(-1.0% ~ 0.0%)은 0.05% 간격으로 세분화 고려

### 2-2. Sample Sparsity

**문제**

71개 공고 기반. 전체 참여자 44,044건은 글로벌 분포에는 충분하지만:

| 필터 조건 | 예상 공고 수 | 예상 참여자 수 | 낙찰자 수 |
|-----------|-------------|----------------|-----------|
| 전체 (글로벌) | 71 | 44,044 | 71 |
| 공종=실내건축 | ~50 | ~31,000 | ~50 |
| 지역=경기 | ~20 | ~12,400 | ~20 |
| 발주처=특정 교육청 | ~3 | ~1,860 | ~3 |

발주처 필터링 시 낙찰자 N=3이다.  
60개 bin에 낙찰자 3명 → 57개 bin의 `win_count = 0`.

이 상태에서 `win_count/count` 계산은 0 또는 무의미한 값만 반환한다.

**현재 설계의 해결책이 없다**: spec에 "71개 공고 기반 (통계 제한적)"으로 기록만 됐을 뿐,  
데이터 부족 시 무엇을 보여줄지 명세가 없다.

**대응 방향**
- 최소 공고 수 threshold 정의: N < 10이면 글로벌 분포 fallback
- 각 bin의 sample size를 응답에 포함 (`count`, `win_count`를 UI에 노출)
- 빈도수가 낮은 구간은 시각적으로 구분 (투명도 낮춤 등)

---

### 2-3. Regional Bias

**문제**

전체 71개 공고가 특정 지역에 편중됐을 가능성이 높다. 수도권(경기/서울/인천) 발주 비중이 높은 현실에서, 글로벌 분포는 사실상 "수도권 편향 분포"다.

- 지방 중소 발주처 공고: 참여자 수 적음(30~80명), 입찰 패턴이 다름
- 대규모 수도권 공고: 참여자 수 많음(300~600명+), 전략적 입찰 패턴 강함

이 두 유형을 합쳐 하나의 글로벌 분포를 만들면, 지방 소규모 공고를 이 분포로 분석할 때 잘못된 인사이트를 제공한다.

**대응 방향**
- 공고별 참여자 수를 메타데이터로 제공 (`estimated_participants`는 이미 있음)
- 참여자 수 구간(30~100명 / 100~300명 / 300명+)에 따른 별도 분포 제공 고려

---

### 2-4. Temporal Drift

**문제**

설계에 시간 가중치가 없다. 2023년 데이터와 2026년 데이터가 동일 가중치로 풀링된다.

입찰 시장에서 시간에 따른 변화:
- 매크로 업체 등장: 특정 끝자리에 대규모 집중 현상 발생
- 법규 변경: 낙찰하한율 기준 변경
- 경기 변화: 불황기에는 낙찰가 하락 압력 증가 → offset 분포 이동

**실증적 위험**: 2023년에는 -0.6% 구간에 낙찰자가 집중됐지만, 2026년에는 -0.4%로 이동했을 수 있다. 현재 설계는 이 drift를 감지하거나 반영하지 않는다.

**대응 방향**
- 수집 날짜 기반 지수 가중치 적용 고려: 최근 12개월 × 2, 이전 데이터 × 1
- 또는 최근 N개월 필터 옵션 제공 (요청 파라미터에 `months_back` 추가)
- 분포의 시계열 변화를 별도로 시각화하는 관리 화면 필요

---

### 2-5. Winner Concentration Distortion

**문제**

낙찰자는 구조적으로 특정 구간(-0.5% ~ -0.8%)에 집중된다. 이 집중의 원인이 두 가지인데, 설계가 이를 구분하지 않는다:

**원인 A** (경쟁자 전략): 업체들이 경험적으로 그 구간이 유리하다고 학습해 몰린다 → 인과  
**원인 B** (예정가격 구조): 복수예비가격 ± 편차가 ±2% 내외이므로, 하한가 근처(-0.5%~-0.8%)가 낙찰 가능성 있는 구간의 하단이다 → 기계적 결과

현재 데이터로는 두 원인을 분리할 수 없다. 따라서 "이 구간에서 낙찰 빈도가 높다"는 사실이 "이 구간에 입찰하면 유리하다"는 전략 근거가 되지 않는다.

극단적 예: 모든 입찰자가 -0.6%에 몰리면, 예정가격이 거기 착지해도 경쟁이 극심해 낙찰 확률은 오히려 낮아진다.

---

### 2-6. win_count / count의 문제점

**수식**

```
historical_win_rate(bin) = win_count(bin) / count(bin)
```

**위반하는 통계적 가정들**

| 가정 | 실제 상황 | 결과 |
|------|-----------|------|
| 각 시행이 독립 | 같은 공고의 참여자들은 상호 의존 (한 명이 이기면 나머지는 짐) | 분모가 과대계상 |
| 공고별 시행 조건 동일 | 참여자 수가 공고마다 다름 (50명 ~ 600명) | 풀링이 부적절 |
| bin 내 모든 입찰이 동질적 | 같은 bin에서도 끝자리 1원 차이로 순위 결정 | 과도한 집계 |

**구체적 수치 예시**

```
bin: offset = -0.6%
  공고 A (50명 참여): 이 bin에 입찰자 5명, 낙찰자 1명 → 로컬 win_rate = 20%
  공고 B (500명 참여): 이 bin에 입찰자 50명, 낙찰자 1명 → 로컬 win_rate = 2%

풀링 후 global win_rate = 2 / 55 = 3.6%

이 3.6%는 A도 B도 아닌 숫자다.
```

**대응 방향**
- 이름을 `historical_win_rate`로 변경
- 공고 수(N) 표시 필수: "N=71개 공고 기반"
- 참여자 수 normalized win rate 계산 고려: `Σ(1/participants_i × I(win_i in bin)) / Σ(I(bid_i in bin))`

### 2-7. Percentile Metric의 실제 의미

**현재 정의**

```
percentile = 내 offset보다 낮은 역사적 입찰 비율
           = P(historical_bid < my_bid)
```

**의미하는 것 vs 의미하지 않는 것**

```
percentile = 30%:
  의미 O → "과거 입찰 중 30%는 나보다 낮은 금액을 냈다"
  의미 X → "나는 상위 70% 입찰자다"
  의미 X → "낙찰 확률 70%"
  의미 X → "이 포지션이 최적이다"
```

낙찰 여부는 예정가격(=무작위)이 내 입찰금액보다 크냐 작냐의 문제다.  
내 금액이 몇 퍼센타일이냐는 이 결정에 직접적으로 개입하지 않는다.

**사용자 오해 패턴** (예상)

> "percentile 15%면 낮은 가격이니까 낙찰 가능성 높겠지?"  

→ 그렇지 않다. 예정가격이 낮게 나오면(복수예비가격이 하향 집중) percentile 15%가 낙찰될 수 있다.  
예정가격이 높게 나오면 percentile 70%도 낙찰될 수 있다. percentile은 예정가격 위치를 모르는 상태에서는 전략 정보가 아니다.

**대응 방향**
- percentile을 "내 가격이 시장에서 얼마나 공격적인 포지션인지"의 지표로 명확히 재정의
- "낙찰 확률"과 섞이지 않도록 UI에서 분리 표시

---

### 2-8. Smoothing 필요성

**문제**

0.1% 간격 raw 히스토그램은 다음 경우에 spike/hole이 생긴다:

- 특정 bin에 매크로가 몰려 비정상적 count 발생
- 인접 bin인데 count가 0 ↔ 50으로 급변
- 낙찰자 집중 구간에서 win_rate가 0% → 5% → 0% → 3% 로 점프

시각적으로는 잡음처럼 보이고, 사용자가 "이 bin만 피하면 된다"고 과잉 반응할 수 있다.

**대응 방향**
- 시각화 레이어에서 3-bin 이동 평균 적용 (단순, 즉시 가능)
- 또는 Gaussian KDE로 continuous density 추정 (통계적으로 우수하지만 구현 복잡)
- win_count가 5 미만인 bin: smoothing 전 raw 값 신뢰 불가 표시

---

### 2-9. Confidence Interval 필요성

**현재 설계**: point estimate만 반환.

```json
{ "offset_pct": -0.6, "count": 45, "win_count": 2 }
```

**win_rate = 2/45 = 4.4%**지만, 95% Wilson Confidence Interval은:

```
n=45, k=2: 95% CI = [0.8%, 15.2%]
```

point estimate 4.4%와 CI [0.8%, 15.2%]의 차이가 크다. 사용자는 4.4%를 신뢰하지만 실제로는 0.8%일 수도, 15.2%일 수도 있다.

n이 작을수록 CI는 더 넓어진다:

| n (count) | k (win_count) | win_rate | 95% CI |
|-----------|---------------|----------|--------|
| 5 | 1 | 20.0% | [3.6%, 62.4%] |
| 20 | 2 | 10.0% | [2.8%, 31.4%] |
| 100 | 5 | 5.0% | [2.1%, 11.3%] |
| 500 | 25 | 5.0% | [3.4%, 7.3%] |

현재 데이터 규모(총 낙찰자 71명)에서 대부분의 bin은 n < 20이다.  
CI 없이 point estimate만 표시하면 정밀도를 실제보다 높게 암시한다.

**대응 방향**
- API 응답에 `win_count_ci_low`, `win_count_ci_high` 추가 (Wilson score)
- 또는 `count`를 노출하고 프론트엔드에서 bar 두께로 신뢰도를 시각화
- count < 10인 bin은 opacity를 낮춰 "데이터 부족" 표시

## 3. 위험 수준 요약

| 위험 요소 | 심각도 | 발생 확률 | 설계 변경 필요 |
|-----------|--------|-----------|----------------|
| win_count/count 오해 | **높음** | 확실 | 이름 변경 + 설명 추가 (필수) |
| Descriptive/Strategic 혼동 | **높음** | 확실 | UI 문구 수정 (필수) |
| Sample sparsity (발주처 필터) | **높음** | 높음 | Fallback 로직 명세 (필수) |
| Temporal drift | **중간** | 중간 | 날짜 파라미터 추가 (권장) |
| Percentile 오해 | **중간** | 높음 | UI 재정의 (권장) |
| Winner concentration distortion | **중간** | 확실 | 문서화로 충분 |
| Confidence interval 부재 | **중간** | 확실 | count 노출만으로 임시 대응 가능 |
| Regional bias | **낮음** | 높음 | 데이터 확대 후 처리 |
| Binning bias (근사 오차) | **낮음** | 낮음 | 정확한 JOIN 쿼리로 해결 |
| Smoothing 부재 | **낮음** | 중간 | 이동 평균으로 간단 해결 |

## 4. 설계 수준 수정 제안

현재 spec에서 아래 항목을 수정해야 구현 시 오해가 없다.

### 4-1. 필드명 변경

```
변경 전: estimated_win_prob
변경 후: historical_win_rate

변경 전: my_position.estimated_win_prob
변경 후: my_position.historical_win_rate
```

### 4-2. 응답에 신뢰도 메타데이터 추가

```json
{
  "data_quality": {
    "total_bids":    44044,
    "total_notices": 71,
    "date_range":    ["2024-01-01", "2026-05-01"],
    "filter_applied": "global"
  }
}
```

### 4-3. 데이터 부족 시 명시

```json
{
  "offset_pct": -0.6,
  "count": 3,
  "win_count": 0,
  "is_sparse": true
}
```

### 4-4. 시스템 포지셔닝 재정의

현재 spec 표현:
> "낙찰 확률 지형도"

수정 제안:
> "경쟁자 입찰 분포 지도 — 이 공고에서 다른 업체들이 어디에 입찰할지를 과거 패턴으로 보여줍니다.  
> 낙찰 확률을 보장하지 않으며, 예정가격은 개찰 전까지 알 수 없습니다."

## 5. 정리

```
현재 설계로 할 수 있는 것:
  ✔ 시장 참여자들이 역사적으로 어디에 입찰했는지 보여주기
  ✔ 내 입찰 가격이 시장에서 얼마나 공격적/보수적인지 위치 파악
  ✔ 낙찰자들이 역사적으로 어느 구간에 집중됐는지 시각화

현재 설계로 할 수 없는 것:
  ✘ 이 공고에서 내 낙찰 확률 예측
  ✘ 최적 입찰 금액 추천
  ✘ 예정가격 위치 예측

올바른 자기 정의:
  "시장 지도(Market Map)"
  사용자가 방향을 정하는 데 쓰는 참고 도구.
  예언 모델이 아니다.
```
