# 투찰 기록과 낙찰선 대조 — 설계

*2026-08-25*

## 무엇을 만드는가

매일 올라오는 공고 중 투찰한 것을 기록해 두고, 개찰 결과가 들어오면
**그때 본 분포 위에 실제 낙찰선을 겹쳐** 보여준다.

두 부분으로 나뉘고, 순서가 있다.

- **Phase 1 — 수집 경로를 info21c 로 바꾸고 공백을 자동으로 메운다.** 결과가 들어와야 대조할 것이 생긴다.
- **Phase 2 — 투찰 기록(`my_bids`)과 대조 화면.**

Phase 2 는 Phase 1 없이도 동작한다(수동 수집으로도 결과는 들어온다). 다만 Phase 1 이
없으면 결과를 사람이 챙겨 넣어야 한다.

## 왜 "낙찰선 적중"인가

측정 기준으로 두 후보가 있었다.

- A. 내 위치 정확도 — 예상 percentile ↔ 실제 percentile
- B. 낙찰선 적중 — 내가 본 분포에서 실제 낙찰가가 떨어진 자리

**B 를 고른다.** 근거는 이미 측정돼 있다.

1. 사정률은 복수예비가격 구조상 사실상 난수다(avg≈1.0, std≈0.007, 44,044건 기준).
   예측 대상이 랜덤이면 정확도를 올릴 여지가 원리적으로 없다.
2. win% 캘리브레이션 Spearman **+0.977** — 단순 빈도 집계가 이미 천장이다.
3. 최적 자리(-0.6%)에 정확히 넣어도 실제 win% 는 약 **0.9%** 였다. 낙찰률의 병목은
   예측이 아니라 경쟁(추첨) 구조다.

A 는 "분포 예측이 얼마나 정확한가"를 재는데, 위 셋에 따르면 그 숫자가 좋아져도
낙찰률은 움직이지 않는다. B 는 "이 발주처에서 낙찰선이 실제로 어디 떨어지는가"를
쌓고, 이는 백테스트에서 유일하게 유의미했던 레버에 직접 들어간다 —
**client(발주처) 분포: 적중 81.1% vs global 72.3%, +8.8%p.**

같은 백테스트가 남긴 3순위 액션이 "client 커버리지↑(74.6%) — 발주처 데이터 추가
수집이 최대 레버" 였다. 이 문서가 그것이다.

# Phase 1 — info21c 자동 수집

## 지금 무엇이 어긋나 있나

`app/jobs/collect.py` 는 `G2BCollector` 를 쓴다. 그런데 G2B 수집이 가져오는 참여자
정보는 **"참여자 수" 정수 하나**(`bids_history.participants`)뿐이다. 분포 엔진이 먹는
`bid_participants.bid_rate`(개별 투찰가)는 info21c 경로에서만 나온다.

**즉 지금의 자동 수집을 켜도 분포 데이터는 한 건도 쌓이지 않는다.**
서버 스케줄러는 `enabled: false` 로 꺼져 있다.

info21c 경로(`scripts/info21c_participants.py`)는 이미 검증된 상태다 — 5,750건 처리
이력(4,726 성공 / 1,011 스킵 / 13 실패), xlsx 12,126개 확보. 마지막 수집은
**2025-12-24** 이고 이후 8개월이 비어 있다.

## 실행 형태

info21c 는 Playwright 로 로그인해 Excel 을 받는다. 서버는 RAM 956MB 중 472MB 만
남아 Chromium 상시 구동에 맞지 않고, info21c 는 동시 접속이 안 돼 스케줄러와 사람이
계정을 나눠 쓰면 충돌한다. 따라서 **로컬 PC 에서 수집하고 결과만 서버로 올린다.**

PC 를 매일 켜지는 않으므로, Windows 작업 스케줄러의 **"예약된 시작을 놓친 경우
가능한 한 빨리 작업 실행"** 을 쓴다.

```
매일 새벽 3시 트리거 + 놓친 작업 따라잡기
        ↓
켜져 있으면 그때, 꺼져 있었으면 다음에 켜질 때 실행
        ↓
get_collected_dates() 로 "마지막 수집일 ~ 어제" 중 빈 날짜만 계산
        ↓
그 구간만 수집 (며칠 비었든 한 번에 따라잡음)
```

며칠을 건너뛰어도 다음 실행에서 메워지므로 "매일 켜야 한다"는 제약이 사라진다.
중복 수집도 `get_collected_dates()` 가 걸러낸다.

## 만들 것

| 대상 | 내용 |
|---|---|
| `app/jobs/collect.py` | `G2BCollector` → info21c 수집으로 교체. 빈 날짜 계산 → 수집 → 적재 |
| `scripts/daily_collect.py` | 그대로 진입점으로 쓴다 (경로 문자열이 `C:\Users\Lenovo\...` 로 낡아 있어 수정 필요) |
| 작업 스케줄러 등록 | 문서화만. 등록은 사용자가 GUI 에서 한다 |

기존 부품을 그대로 쓴다 — `get_collected_dates()`(빈 날짜 계산), `BackfillState`(진행률).

## 첫 실행 주의

8개월치(2025-12-24 이후)를 한 번에 따라잡으려 하면 오래 걸린다. **첫 회는 수동으로
기간을 나눠 돌리고**, 그 뒤부터 스케줄러에 맡긴다.

# Phase 2 — 투찰 기록과 대조

## 데이터 모델

새 테이블 하나를 만든다. `bids_history` 에 컬럼을 붙이지 않는 이유는, 그 테이블이
시장 데이터이고 모든 분포 쿼리가 읽는 곳이기 때문이다. 개인 기록을 섞으면 오염된다.

```
my_bids
  id                  INTEGER  PK
  project_id          VARCHAR(50)   공고번호. bids_history.project_id 와 조인
  notice_title        VARCHAR(200)  공고명 (목록 표시용, 선택)
  client_name         VARCHAR(100)  투찰 시점 발주처
  my_bid_price        BIGINT        내 투찰가 (원)
  base_price          BIGINT        투찰 시점 기초금액
  lower_limit_rate    NUMERIC(10,8) 투찰 시점 낙찰하한율
  my_offset_pct       NUMERIC(8,4)  투찰 시점 내 offset
  my_percentile       NUMERIC(6,2)  투찰 시점 내 위치
  snapshot_json       TEXT          그때 받은 distribution 응답 통째
  bid_date            DATE          투찰일
  created_at          TIMESTAMP
  UNIQUE(project_id)
```

**`snapshot_json` 이 이 설계의 핵심이다.** 데이터는 매일 쌓이므로 3개월 뒤 같은
공고로 분포를 다시 계산하면 그때 본 그림과 달라진다. 스냅샷 없이 사후 재계산으로
비교하면 "내가 그때 본 판단 근거"가 아니라 "지금 알게 된 것"과 비교하게 되어
적중 여부가 무의미해진다. 히스토그램 182구간 기준 수 KB 수준이라 통째로 남긴다.

개찰 결과는 **저장하지 않는다.** `bids_history` 에 이미 들어오므로 조회 시 조인한다.
같은 사실을 두 곳에 두면 어긋난다.

## 대조 로직

```
my_bids ⋈ bids_history ON project_id

bids_history.winner_price 가 있으면 → 개찰 완료
    실제 낙찰 offset = winner_price / base_price - lower_limit_rate
    내 거리(%p)      = my_offset_pct - 실제 낙찰 offset
    낙찰선이 스냅샷 히스토그램의 어느 구간이었는지 = snapshot_json 에서 조회
없으면 → 개찰 대기
```

`base_price` 와 `lower_limit_rate` 는 **스냅샷의 값을 쓴다.** 나중에 수집된 값이
다를 수 있고, 그때의 판단 근거를 재현하는 것이 목적이기 때문이다.

## API

| 메서드 | 경로 | 내용 |
|---|---|---|
| POST | `/api/v1/my-bids` | 투찰 기록 저장 (아래 참조) |
| GET | `/api/v1/my-bids` | 목록. 개찰 여부·대조 결과 포함 |
| GET | `/api/v1/my-bids/{project_id}` | 상세. 스냅샷 + 실제 낙찰선 |
| DELETE | `/api/v1/my-bids/{project_id}` | 잘못 기록한 것 삭제 |
| GET | `/api/v1/my-bids/summary` | 발주처별 실제 낙찰선 offset 중앙값 |

`POST` 는 프론트가 방금 받은 distribution 응답 **전체**와 `my_bid_price`,
`notice_title`(선택)을 함께 보낸다. 서버가 분포를 다시 계산하지 않는 이유는,
재계산하면 사용자가 화면에서 본 것과 저장되는 것이 어긋날 수 있기 때문이다.
저장하는 것은 "사용자가 실제로 보고 판단한 그림"이어야 한다.

`notice_title` 은 분포 응답에 없다. G2B 조회가 성공하면 거기서 오고, mock 이거나
`overrides` 로 직접 넣은 경우에는 사용자가 목록에서 알아볼 수 있게 직접 적는다.
비어 있어도 `project_id` 로 식별되므로 기능은 동작한다.

## 전제와 미해결

- **서버 데이터가 낡았다.** 서버는 `bids_history` 467건 / `bid_participants` 52행
  (공고 1건분)뿐이라 지금 서버에서는 분포가 나오지 않는다. 로컬은 12,445건 /
  4,637,505행. **Phase 2 를 서버에서 쓰려면 데이터 이관이 선행돼야 한다.**
- **서버 코드 동기화가 막혀 있다.** 서버 git 브랜치 이동이 auto 모드 분류기에
  차단돼 코드를 올리지 못했다.
- **스키마 버전이 갈라져 있다.** 로컬 `37e6818cd693`, 서버 `b7e2d4f8a1c3`.
  로컬 alembic head 가 두 갈래(`37e6818cd693`, `54acb1bf74ff`)로 분기해 있어
  마이그레이션 전에 정리가 필요하다.
- **ETL 이상치가 계속 유입된다.** 조회 시점에서 `0.5 <= bid_rate <= 1.05` 로 막았을
  뿐 `scripts/etl_participants.py` 는 그대로다. Phase 1 로 수집을 재개하면 이상치도
  함께 쌓인다.
- **`client_id` 는 여전히 전 행 `'None'`.** 우회만 했고 값을 채우지 않았다.
  client 레벨 fallback 은 `client_name` 으로만 선다.
